# Deploying AskScotty

Local development is [README.md](../README.md) and `./setup.sh`. This is the
public deployment: an API judges can hit and an app they can open, on three free
tiers.

| Piece | Host | Cost |
|---|---|---|
| Django API | Render, Docker web service | $0 |
| Expo web build | Render, static site | $0 |
| Postgres + pgvector | Neon | $0 |

Both Render services come from one blueprint, so there is a single GitHub
connection and both redeploy on push.

Neon rather than Render's own Postgres because Render's free database **expires
30 days after creation**. Neon's does not, and both support pgvector.

The real cost is Anthropic and OpenAI tokens. Set a spend limit in the Anthropic
console before the URL goes anywhere public — see [Cost](#cost).

## What the stack forces

Worth knowing before substituting a host, because three of these rule out the
obvious cheap options:

- **`/api/ask/stream/` is SSE**, and a worker is held for the whole life of the
  stream. Anything serverless — Vercel functions, Netlify, Lambda — buffers the
  response and caps the request at 10–60s. It cannot host this API.
- **Answers take 30–120s.** Any proxy or worker timeout under ~180s cuts them off
  mid-thought.
- **pgvector with an HNSW index.** The first migration runs `CREATE EXTENSION
  vector`, so the database role must be allowed to.
- **`EXPO_PUBLIC_API_URL` is baked into the JS bundle at build time**, so the API
  must exist before the app is built. That fixes the order of everything below.

## Deploy

### 1. Database — Neon

Create a project at [neon.tech](https://neon.tech) (Postgres 16). From
**Connection Details**, keep the host, database, role and password.

Nothing else to do here: the extension and the HNSW index are created by
`manage.py migrate`, which `entrypoint.sh` runs on every container boot.

### 2. Provision the planner

The planner talks to a Managed Agents agent that has to exist before any question
can be answered. Locally:

```bash
docker compose exec backend python manage.py provision_planner
```

It prints `PLANNER_AGENT_ID` and `PLANNER_ENVIRONMENT_ID`. **Both are scoped to
the Anthropic organisation behind your API key** — they are not secret, but they
are also not portable between accounts. Keep them for step 3.

### 3. Render — both services

Dashboard → **New** → **Blueprint** → pick this repo, branch `deploy`.
[render.yaml](../render.yaml) declares the API and the app, and prompts for each
secret. Fill in:

| Prompt | Value |
|---|---|
| `POSTGRES_HOST` / `_DB` / `_USER` / `_PASSWORD` | from Neon, step 1 |
| `ANTHROPIC_API_KEY` | console.anthropic.com |
| `PLANNER_AGENT_ID` / `PLANNER_ENVIRONMENT_ID` | from step 2 |
| `OPENAI_API_KEY` | platform.openai.com |
| `CORS_ALLOWED_ORIGINS` | leave blank for now — step 5 |
| `CSRF_TRUSTED_ORIGINS` | leave blank for now — step 5 |
| `EXPO_PUBLIC_API_URL` | leave blank for now — step 5 |

Three values are left blank because each names a URL that does not exist until
Render has assigned the hostnames. They cannot be wired with `fromService`: that
yields a bare hostname, and all three need the scheme.

`DJANGO_SECRET_KEY` and `CONNECTOR_ENCRYPTION_KEY` are generated by Render.
`DJANGO_ALLOWED_HOSTS` wires itself to the service hostname.

When the deploy goes green, `https://<service>.onrender.com/api/health/` should
return JSON.

### 4. Load the campus index

The API is up but knows nothing: [rag_index.sql.gz](../backend/fixtures/rag_index.sql.gz)
carries the ~1,400 crawled chunks and their embeddings, and it has to be pushed
into Neon once.

```bash
./scripts/restore_index.sh 'postgresql://user:pass@host/db?sslmode=require'
```

Needs `psql`; if the host has none, the script falls back to the one inside the
running compose `db` container, so `docker compose up -d db` is enough. It refuses
to run twice.

Skip this and every campus question returns nothing found — which looks like a
broken planner rather than an empty index.

### 5. Point the two services at each other

Both hostnames now exist. On **askscotty-app** set:

```
EXPO_PUBLIC_API_URL=https://askscotty-api.onrender.com
```

and on **askscotty-api**, with no trailing slash:

```
CORS_ALLOWED_ORIGINS=https://askscotty-app.onrender.com
CSRF_TRUSTED_ORIGINS=https://askscotty-app.onrender.com
```

Each save triggers a rebuild, which is what bakes the API URL into the bundle.

**Not optional.** `CORS_ALLOW_ALL_ORIGINS` is only on while `DEBUG` is, so until
`CORS_ALLOWED_ORIGINS` is set every browser request fails — and it surfaces in
the app as a bare "network error" rather than anything mentioning CORS.

## Cold starts

Render's free tier spins a service down after 15 minutes idle and takes ~50s to
come back. On top of a 60s answer that is a poor first impression for a judge.

Either:

- Put the service on **Starter ($7/mo) for the judging window**. Render prorates
  by the second, so three days is about $0.70. Downgrade after.
- Or stay free and keep it warm with an uptime pinger (cron-job.org, UptimeRobot)
  hitting `/api/health/` every 10 minutes.

Neon also scales to zero and adds ~500ms on the first query. Harmless alone, but
it stacks with a cold start.

## Cost

Hosting is $0 (or ~$0.70 with the Starter window). Tokens are the real spend, and
the deployed URL is **unauthenticated** — anyone who finds it can spend your
balance.

- `PLANNER_SESSION_BUDGET_CENTS` is set to 100 in the blueprint, down from 500
  locally. It caps one conversation thread, not the account.
- Set a hard monthly limit in the Anthropic console. That is the only real
  backstop; the session budget is a runaway-loop guard.

## What the deployed build does not do

`DEBUG=false` unmounts the browser extension's cookie-ingestion routes
([config/urls.py](../backend/config/urls.py)), by design — they were never meant
to face the internet. So **Piazza and Gradescope answers only work locally**. Plan
the demo accordingly: public campus questions on the deployed URL, personal
connectors on a laptop.

## If the judges run it from source

They need Docker, Node LTS, and their own `ANTHROPIC_API_KEY`. Then:

```bash
./setup.sh
```

It creates both `.env` files, starts Postgres and the API, restores the campus
index, provisions a planner agent against *their* key and writes the two ids back
into `.env`. `.env.example` deliberately ships those ids blank — filling them with
ours would point their key at an agent it cannot access, and every question would
fail with "not provisioned".

Without an `ANTHROPIC_API_KEY` the app still starts and still shows the UI, but
cannot answer.

## Troubleshooting

| Symptom | Cause |
|---|---|
| Every question fails, "not provisioned" | `PLANNER_AGENT_ID` empty, or minted under a different Anthropic org |
| App shows "network error" on every request | `CORS_ALLOWED_ORIGINS` not set, or has a trailing slash |
| App calls the wrong API host after a URL change | Bundle built from Metro's cache — needs `--clear` |
| Campus questions find nothing | Step 4 never ran |
| Answers cut off around 30s | `--timeout` missing from the gunicorn CMD |
| Answers are vague, citations thin | `OPENAI_API_KEY` unset — retrieval fell back to full-text only |
| 403 on `/admin/` login | `CSRF_TRUSTED_ORIGINS` missing the API's own origin |
| First request of the day takes a minute | Free-tier cold start — see above |
| Deploy never goes live, health check 400s | `DJANGO_ALLOWED_HOSTS` missing the real hostname — Django's `DisallowedHost`, which logs as a bare 400 |

Logs are `docker compose logs -f backend` locally, or the **Logs** tab on Render.
To confirm the toolset registered at all:

```bash
docker compose exec backend python manage.py shell -c \
  "from apps.tools.registry import tools_for_session; print([t.name for t in tools_for_session(None)])"
```

An empty list means a tool module never imported, and every question is being
handed a toolset of nothing.
